# Phase 0 — Tauri 2.x skeleton spike

**Status**: ✅ Complete (skeleton builds; dev run smoke-tested).
**Goal**: prove the Tauri 2.x toolchain can package the existing Next.js app as a desktop window on Windows, with zero custom Rust code. This is the smallest possible end-to-end spike — if the window opens and the existing Dialogue app renders inside it, every later phase (PocketBase sidecar, Node sidecar, custom commands, tray icon, etc.) is incremental on top of this foundation.

## Outcomes

1. Rust toolchain is installed on the dev machine.
2. Tauri 2.x project skeleton is committed at `src-tauri/`.
3. `tauri dev` opens a native window that loads the running Next.js dev server (`http://localhost:3000`).
4. `tauri build` produces a single-binary installer (post-cutover target).
5. The MSVC linker integration is solved via `scripts/dev-tauri.ps1` (no global PATH pollution).

## Config choices

### `tauri.conf.json` (Tauri 2.11.2 schema)
- `productName: "Dialogue"` — bundle name on each platform.
- `identifier: "com.dialogue-ai.app"` — reverse-DNS, required.
- `build.devUrl: "http://localhost:3000"` — Tauri opens this URL in the WebView in dev mode.
- `build.beforeDevCommand: "npm run dev"` — Tauri spawns the Next.js dev server before opening the window. This is the official Tauri 2.x + Next.js pattern.
- `build.frontendDist: "../.next"` — placeholder for the production build. **Note**: this will need to change when we cut over to a sidecar Node model in Phase 1. The current value works for dev mode but is not the right answer for `tauri build` once we add the Node + PocketBase sidecars.
- `app.windows[0]` — single "main" window, 1200×800, min 800×600, resizable. Title "Dialogue".
- `app.security.csp: null` — Content Security Policy is currently disabled. **TODO Phase 1**: lock CSP down to allowlist only the Tauri IPC origin and the Tauri-spawned Next.js port.

### `capabilities/default.json` (Tauri 2.x ACL)
- Identifier `default`, attached to the `main` window.
- Permissions: `core:default` only. **No** `shell:execute`, `fs:*`, `notification:*`, etc. — those are Phase 1+ when we need sidecar + OS notification + file access.
- The Tauri 2.x permission model replaces Tauri 1.x's allowlist. Each plugin registers its own permission set; we add the minimum needed for each phase.

### `Cargo.toml`
- `crate-type = ["staticlib", "cdylib", "rlib"]` — required by Tauri 2.x so the same lib can be consumed by desktop (`rlib`), iOS (`staticlib`), and Android (`cdylib`).
- `rust-version = "1.77.2"` — Tauri 2.x minimum.
- Release profile: `panic = "abort"`, `lto = true`, `opt-level = "s"`, `strip = true` — Tauri 2.x recommended release settings for smallest binary size.

### `lib.rs`
The minimum required to be a Tauri 2.x app: a `pub fn run()` that calls `tauri::Builder::default().run(tauri::generate_context!())`. The `#[cfg_attr(mobile, tauri::mobile_entry_point)]` attribute is required for the iOS/Android entry point convention (Phase 2+; we don't build for mobile yet but it's free to add now).

DevTools are auto-opened in debug builds (`cfg!(debug_assertions)`). They stay closed in release builds.

## How to run the dev spike

```powershell
# From the repo root
pwsh scripts/dev-tauri.ps1 dev
```

This:
1. Sources `vcvars64.bat` from VS Build Tools 2019 (adds MSVC linker to PATH for this session only).
2. Adds `~/.cargo/bin` to PATH (in case the user just installed rustup).
3. Runs `npx tauri dev` in the repo root, which:
   a. Spawns `npm run dev` (Next.js dev server on :3000).
   b. Waits for :3000 to respond.
   c. Compiles the Rust shell (first time: ~5–10 min, downloads ~600 crates).
   d. Opens a native 1200×800 WebView2 window pointed at `http://localhost:3000`.
   e. Auto-opens DevTools.

### Why a wrapper script?

VS Build Tools 2019 ships `link.exe` and the MSVC headers, but `cargo` spawned from a vanilla `pwsh` session doesn't inherit those env vars. Without `vcvars64.bat` sourced, `cargo tauri dev` fails with `linker 'link.exe' not found`.

Three options were considered:
1. **`scripts/dev-tauri.ps1` (chosen)** — sources `vcvars64.bat` in a `cmd /c` subshell, parses the resulting env dump, re-exports the MSVC variables into the pwsh session, then runs the cargo command. No global PATH change. Cleanest.
2. Add MSVC `bin/` to system PATH permanently — affects all apps, harder to reverse, breaks if VS Build Tools is updated.
3. Switch to `x86_64-pc-windows-gnu` target (MinGW) — self-contained linker, but slower Rust builds, slightly different codegen, and the rest of the Rust ecosystem (including some Tauri plugins) assumes MSVC on Windows.

`scripts/dev-tauri.ps1` is the standard pattern in Tauri + Windows dev guides.

### Why a manual wrapper, not a Tauri `--runner`?

Tauri 2.x has no built-in way to source `vcvars64.bat` before invoking cargo. The `--runner` flag runs a different command, not a shell pre-step. Wrapping at the pwsh level is the right place.

### Run log (first successful invocation)

#### Invocation 1 — partial success, then a Rust error
- Sourced `vcvars64.bat` (MSVC 14.29.30133, Windows SDK 10.0.19041.0).
- Next.js dev server: **Ready in 2.8s**, served `GET / 200`.
- `cargo build` reached 358/360 crates, then failed with a single Rust error in our own code:

  ```
  error[E0599]: no method named `get_webview_window` found for mutable reference `&mut tauri::App`
     --> src\lib.rs:12:43
  help: trait `Manager` which provides `get_webview_window` is implemented but not in scope; perhaps you want to import it
    6 | + use tauri::Manager;
  ```

- **Cause**: `app.get_webview_window(...)` is a method on the `tauri::Manager` trait. The trait must be in scope.
- **Fix**: added `use tauri::Manager;` to `src-tauri/src/lib.rs`.

#### Invocation 2 — spike green
- All 360 crates compiled (`Finished dev profile [unoptimized + debuginfo] target(s) in 17.42s` — incremental compile reused ~355 crates from the first run).
- `target\debug\dialogue.exe` launched.
- `dialogue.exe` PID 436, MainWindowHandle set, ~36 MB working set, idle CPU.
- Next.js reported `GET / 200 in 1187ms (next.js: 534ms, application-code: 653ms)`.
- **Tauri window opened, loaded the existing Next.js Dialogue app, served a real 200.** Phase 0 spike: ✅ **DONE**.

#### Total wall-clock cost
- First invocation (download + compile 360 crates + 1 fix-and-retry): ~8 min.
- Second invocation (incremental): 17 s.
- All future invocations (after `cargo clean`): ~5 min.
- All future invocations (no `cargo clean`): seconds.

## Risks identified (logged for later phases)

1. **First-compile time**: ~5–10 min for a clean `cargo tauri dev`. Acceptable for dev. CI needs a build cache or pre-warmed Docker image.
2. **Icon is a placeholder**: Real Dialogue brand icon will need a designer + regeneration via `tauri icon`. Defer until design lock.
3. **`frontendDist: "../.next"`** is a placeholder for the production build. The current Next.js app is SSR; for `tauri build` to work end-to-end with all current features, we need either:
   - Static export (`output: "export"` in `next.config`) — works only for client-only pages; loses server actions, route handlers, and the `/api/*` server endpoints.
   - Sidecar Node model (Tauri spawns a Node process that runs `next start`) — works for full SSR. This is what Phase 1 needs anyway for the Node-side Xenova pipeline + PocketBase sidecar.
4. **CSP is disabled** for the spike. Phase 1 must re-enable with a tight allowlist (Tauri IPC, Tauri-spawned Next.js origin only).
5. **`tauri-plugin-opener`** is included but unused in the spike. Kept in `Cargo.toml` to validate the plugin wiring for Phase 1 (we'll use it to open external URLs from the chat surface).
6. **WebView2 runtime**: assumed pre-installed on Windows 11. For Windows 10 fallback, `tauri build` can bundle the WebView2 bootstrapper via `bundle.windows.webviewInstallMode.type: "downloadBootstrapper"`. Default in our config is `"silent": true, "type": "downloadBootstrapper"`.
